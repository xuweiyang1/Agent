# 工作流：一步一提交，一提交一推送

两台机器（台式机 + 笔记本）交替开发，靠 GitHub 做唯一的真源和备份。

## 每步的固定动作

```powershell
# 1. 开工前先拉，确保不是在旧状态上动手
git pull --rebase origin main

# 2. 做完一步就提交
git add <本次涉及的文件>
git commit -m "<这一步做了什么>"

# 3. 立刻推送，这一步才算落地
git push origin main
```

## 每步收尾必须更新文档

这一步的固定动作，和 commit 同等重要：

- **`docs/ROADMAP.md`** 的「进度」一节 —— 记下这一步完成了什么、关键数字。
- **`AGENTS.md`** 的进度表 —— 它会被另一台机器的 agent 自动读取。

理由是一次真实事故：另一台机器的 agent 因为仓库里没有进度声明，把 W3 判成
"还没做"。**文档没更新 = 另一台机器在用过期的地图施工。**

如果是新增了可运行的入口（脚本、demo），**README 的 Getting started 也要同步**，
并且要真的照着重跑一遍。

## 三条纪律

- **一步一提交**：提交粒度 = 一个能独立讲清楚的改动，不是"今天干的活"。
- **先拉后改**：开工先 `pull --rebase`。两台机器都在改同一分支，不先拉就是等着冲突。
- **不留未跟踪文件**：任何有价值的产物（文档、注释、笔记）都要提交，否则它只存在于一台机器上，另一台看不到，硬盘坏了就没了。

## 为什么强调"保留备份"

`origin` 不只是同步渠道，是**唯一的异地备份**。本地提交但没推送，等于没有备份；
未跟踪的文件连本地版本控制都没进，风险最高。

## 提交信息怎么写

第一行说清"这一步做了什么"，正文说清"为什么这么做、有什么取舍"。
后面 review 历史时，有价值的是正文里那些取舍，不是第一行。
